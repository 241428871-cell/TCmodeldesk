# 原生主脑控制层

这是隔离重构中的控制内核，尚不是完整工作台。现有主脑控制器已通过 `host_flow.py` 接入 LangGraph，继续使用原项目库、时钟、派发、费用和验收入口。包内还保留独立 SQLite 控制合同、计划持久化、任务审核图及租约参考实现。导入模块、构造仓库和编译图不创建领域记录、不启动服务、不查询账户、不调用模型。

完整产品设计和未完成工作见上级 `docs/完整软件设计.md`、`docs/重构进度.md`。

## 离线检查

Python 3.12，使用 uv 创建本地环境；依赖锁定在 `uv.lock`，不会修改用户的全局 Python。

```sh
uv sync --locked
uv run --locked ruff check src tests
uv run --locked basedpyright
uv run --locked pytest
```

2026-10-23 当前控制层 **269 项**测试通过；完整工作台为 **1777 passed、48 skipped、427 subtests passed**。它们使用临时 SQLite、模拟提供方、真实本地 Python 子进程及随机本机 HTTP 端口，并覆盖持久租约、进程终止恢复、写回接管、owner_epoch、`/btw` 和需求插入。核心 `src/tests` 通过 ruff ALL，完整控制层通过 basedpyright all。真实依赖是 LangGraph 1.2.16、langgraph-checkpoint-sqlite 3.1.2。运行集成组需要 `uv sync --locked --group workbench`。窄类型桥只声明本项目使用的接口，实际执行测试同时约束兼容性；不能用桥声明代替运行验证，也不能据此声称外部宿主、账户或最终桌面外壳已验收。

## 已接入的工作台入口

隔离分支 `.local-worker/goal_controller.py::run_once` 现在调用 `build_host_flow()`，依次执行输入快照、原生回合、动作应用、结算四个控制节点。用户任务阶段仍由主脑动态生成；没有把这四个控制机制当成用户的固定任务阶段。

`goal_graph_bridge.py` 在原 stage_store 项目库中保存 `goal_graph_steps`。checkpoint 只保存目标／意图身份与当前位置，完整上下文和原生结果保留在领域阶段回执。领域回执完成、checkpoint 丢失时可以重建而不重复调用；有副作用阶段仍在 inflight 时拒绝盲目重入。图执行锁与 STOP 的目标授权锁分开，等待主脑不会阻塞用户停止。

新动作阶段使用版本 2 回执，输入快照明确保存动作回执能力、准则及计划版本。`host_effects.py`、`goal_effects.py` 复用原项目的 `brain_requests`：计划、问题、义务和目标完成与回执在同一领域事务提交；派发、审核和交接从原任务或验收记录核对，不重复发送未知请求。批次清单固定原输入，不能给同一轮次替换动作；后续计划修订也不能把旧提案套到新阶段。

`goal_resume.py` 允许原生结果已完成落盘的轮次继续原动作阶段。原图锁内重新核对 RUN、epoch、原 owner、进程创建身份、租约及阶段回执，然后仅借用恢复租约；不创建新轮次、不调用新 CLI、不改变续跑周期。`goal_scan.py` 接入原扫描器，已完成目标仍有动作回执待结算时也先考虑原轮次恢复。恢复失败记为 blocked，保留 UNKNOWN 所有权，不在每次扫描时重复尝试。人工等待、暂停和 STOP 不被失败结果或恢复动作清除。

结算阶段也有显式版本 2：`host_settlement.py` 与 `goal_settlement.py` 将原轮次完成和 SETTLE 回执放在同一项目事务内。原 ACTIONS、NATIVE 已有完成回执且能力声明匹配时，可以恢复 inflight 结算；提交后的丢回复不重复改变时钟，旧回执不能复活 STOP。版本 1、缺少能力声明或未知原生结果仍不自动重发。

原生进程退出不能单独核销图内副作用。`host_resolution*.py` 与 `goal_resolution.py` 提供明确的人工处置：在原图锁内核对完整原轮次、阶段、请求、任务及精确进程证据，再把核对决定与结束原轮次原子保存。浏览器“待审核”已接入此清单，可停止原关联任务、往返只读消息流，填写依据并保留当前工作。它不接受成果，不修改准则、模型、周期或人工暂停／停止，也不把旧请求改写为成功。历史缺少进程证据仍受阻。真实任务／答复事件已接原 GoalGraph；原队列确认与已准备任务的安全补投已接入，新托管任务的初始化中断恢复也已接入；生产任务级 interrupt 仍待完成。独立 ControlStore/RoundStore 不参与该入口，不应另启控制器认领同目标。

`cli_launch.py` 在实际原生 Popen 处再次检查当前授权并先保存 armed 标记，在等待片段与每次写回时检查撤销。新任务的启动协议版本区分可信“未启动”和旧记录缺少 PID；后者不能作为人工核销依据。真实本地 Python 子进程验证了撤销后拒绝写回，未消耗原生账户额度。Codex MCP 内嵌页现在打包全部已声明侧栏、治理、核对和消息流资产，UI 代理补齐精确接口；只有原生输出会话读取允许受限 channel/capture 查询，其他任意查询仍拒绝。DSH 沿用同一 loopback 页面，原生 GUI 验收另记。

`host_decision_scope.py`、`review_artifacts.py`、`review_tasks.py` 与原 `human_decisions` 共用项目记录。新例外使用版本 2 分支指纹，覆盖受影响阶段、完整上游依赖、实际文件字节、原关联任务及验收／交接记录；无关计划修订、文件或任务进展不使待答复卡失效。旧卡和最终审核继续覆盖整个目标。创建与答复复用原目标锁，答复时同时校验原提案关系、版本、准则和 epoch。缺失／外来／损坏／超预算的相关记录拒绝授权；明确的无关损坏记录不会扩大这张卡的范围。批准消费已通过 `decision_grants` 与原阶段认领原子接入：精确绑定原任务，重复认领幂等，原任务恢复须重走认领；执行器只能检查已有回执。消费后的自身输出可变化，上游输入、提案和当前授权继续核对。真实任务及人类答复事件已接原 GoalGraph；生产任务级图自动恢复尚待接入。

`native_commands.py` 统一 Claude/Codex 的权限参数。新目标显式保存 auto；没有权限字段的历史时钟保留 read_only。Codex 使用 on-request、auto_review、workspace-write 的原生组合，适用于新建和 exec resume；Claude 使用原生 auto。运行账户、准则、模型和费用仍由原共享核心检查。这只证明命令映射和离线接线，尚未验证真实账户下的 auto 分类器及全部原生工具边界。

## 已实现的领域命令

- `ControlStore.initialize()` 显式创建或迁移领域库，检查应用标识和 schema 版本。外来库、较新版本和不符合同的 schema 会被拒绝。事务升级失败回滚，普通读取不迁移、不创建不存在的领域库。
- 版本 0 的已知原型库需要显式 `adopt_legacy=True`；版本 1、2 可以按事务升级到版本 3。迁移保留历史控制记录与计划，不会从旧图猜测领域计划。旧目标缺少计划时返回 `plan_not_initialized`，待经核对的导入器补齐。
- `PlanStore.patch()` 同时提交不可变完整修订、任务观察和收据。活动或 UNKNOWN 任务由领域记录判定，主脑不能在补丁中宣称它们已空闲。普通有效重规划无需人类批准。
- `DecisionStore` 提供事项去重、答复、单次消费和失效核对。答复绑定任务内容、相关产物、准则版本和 epoch；增加无关任务不使答复失效。人类身份由未来受信 API 适配器提供，不能把 AI 工具传来的 `actor_id` 当成认证。
- 用户 STOP 在同一事务撤销 outbox 和该目标的开放审核项；这一撤销不依赖解析任务或审核正文，损坏的附属记录不会阻止停止。它仍保留真实运行器尚未退出的状态。

## 独立任务图

`build_task_graph()` 实现独立任务的审核门，不是完整执行图。`interrupt()` 之前只读取已有领域记录，恢复信号只含 decision ID，不能伪造答复。答复消费命令先写入 checkpoint，再由下一节点提交领域事务；领域已提交而图未保存时，重入读取原收据。

`advance_task()` 是有界事件处理入口：发现已保存答复后自动发送对应恢复信号，不要求用户再点击“继续”，也不另开轮询或时钟。调用者仍须持有该图线程的执行锁；当前服务调度器尚未接入这层锁。一个任务等待审核不暂停另一个独立任务图。

## 目标规划与结算

`build_goal_graph()` 将输入准备、首次启动或原操作核对、领域结算分为可持久节点。`RoundStore` 在原 outbox 操作上保存不可变规划输入；原子 arm 只给一个调用者 START。后续重入只允许 `inspect_round()`，不能盲目再次发送提示。早期只读 checkpoint 中控制快照的 `graph.py` 实验已移除，相关用例由当前领域授权检查替代。

运行器回执按操作 ID、receipt ID 和序号去重，过期观察不会覆盖已知结果。UNKNOWN 保留未结算 busy；文件、进程或运行器账本缺失不能自动当成未启动。只有可信运行器证明终止或未发送，以及唯一 START 调用者确认尚未向运行器交接的路径，才能完成对应结算。

计划提交、回合结算和 busy 解除在同一领域事务中完成。终止后到达的结果保留，但不应用计划，不恢复用户意图或时钟。当前计划已经变化或主脑补丁无效时，保存拒绝依据并请求重新规划；不会覆盖新计划。结算一个回合不关闭整个目标，也不重建续跑时间。

租约续期绑定精确 owner 与 expiry，新代使旧代立即失效。旧控制器不能取消已续期的未启动操作。`PlanningRounds` 协议描述独立参考库的规划合同；当前工作台通过 host_flow 适配原生动作全集，没有把既有 StageSpec 缩减后导入此参考库。

## 有意保留的边界

ControlStore 的旧命令回执代表当时的操作，不代表当前授权；消费者必须重新读权威状态。原生调用发出后回执未知、租约过期或用户停止，不能盲目重发。当前 expire 只标记未知，没有实现原生会话核对和恢复证明。

图返回 `ready` 或 finalized 是当时的观察，不是新派发授权；已完成图重读可能返回旧 checkpoint。后续执行端必须重新读取当前 epoch、租约、费用与策略。当前目标图只完成有界规划机制，尚未接入完整的派发、审核、整改与交付动作。Control.busy 表示本控制链未结算续接回合，不能据其假设所有执行工作者都已退出。

SQLite 事务和 authorize 检查不撤销已经被远端接受的动作，也不能单独强制原生 CLI 的每一次工具调用。真实运行器、任务派发与验收节点、人类认证接口、费用预留、API 与 UI 接线仍未完成。每任务准则与产物版本目前是领域合同，还未接现有项目策略及原生产物观察器。现有测试不证明操作系统休眠、机器掉电、真实模型或跨宿主端到端恢复。

原 AAD 的 `goal_controller`、`goal_brain_runner`、`goal_actions`、`continuation_*`、治理与账户后端已按源码迁移；原运行目录与 8765 服务没有被本分支修改。项目／账户／治理静态资产已迁移，新增轻量消息流与只读 CLI 输出检查器。新目标的默认文件范围已改为项目内自主选择；主脑直接编辑、原生工具的记录保护和独立验收仍待形成一致策略。既有 GoalContract/StageSpec 的授权、模型及验收字段没有丢弃。

## 项目范围与 AI 文件选择

`file_authority.py` 是无宿主依赖的路径合同，`goal_file_scope.py` 将其接入原目标、计划、派发前校验及 CLI 写回。人类显式创建新目标而未给文件清单时使用 `project`；主脑为每个编辑阶段选择具体相对文件，可以包含尚未创建的新文件。`selected` 继续精确限制到指定清单，显式空清单不允许编辑。历史缺字段记录按 `selected` 读取，不自动改写；只改准则保留原文件范围和显式最终审核策略。

项目授权仍排除运行记录、账号配置、Git 元数据及运行 home；派发和写回重新解析当前路径，拒绝项目外目标、目录与保护记录别名。测试用真实本地 Python 子进程验证了新文件交付、仅指定文件写回、空项目只读调用，以及执行期间别名改指向记录目录时拒绝写回。CLI 身份持久化失败也会终止并回收本次子进程。这是结构化路径边界，不能据此声称任意原生终端工具获得操作系统级隔离，也不保证多文件写回的事务原子性。

权限映射依据为已安装 CLI 的 help 与官方文档：[Codex 自动审批](https://learn.chatgpt.com/docs/sandboxing/auto-review)、[Codex CLI](https://learn.chatgpt.com/docs/cli/reference)、[Claude 权限](https://code.claude.com/docs/en/permissions)。实际账户支持和权限生效仍需原生验证。

## 消息流与原生输出

`host_trace.py` 用只读 SQLite 连接读取同一项目的实际派发回执和已由原生回合处理的状态输入；任务依赖不生成消息线。每次最多读取 50 轮、500 个任务关联，任务正文总读取预算 2 MiB；投影上限是 100 节点、200 连线和 2000 事件。损坏、归属不一致、未知效果和窗口省略均显式计数。读取不初始化项目、调用 CLI 或驱动时钟。进程状态通过可选宿主探针核对 PID 与创建时间；撤销授权不等于进程已退出。SQLite 只读连接不修改领域记录，WAL 的内部读取锁由 SQLite 管理。

面板 `/api/flow` 与会话输出接口限定到当前具体项目。新 Claude/Codex 执行器把 stdout/stderr 写入每次调用独立的 `native-cli/<capture_id>/`，避免覆盖旧输出；检查器每次最多读取 32 KiB，并标明截断。输出是纯文本，不执行终端转义，也不附加 stdin 或伪装成 PTY。源调用变化时清除跟随，旧 capture_id 不能读成新调用。原生 auto 参数由主脑与 Codex 执行适配器共用纯映射；实际账户是否支持仍待原生验证。

`panel/flow.js` 没有图框架依赖：SVG 连线与 DOM 节点、同投影文字模式、双击/Enter 查看、右键与菜单按钮共用操作。查看时最多每 5 秒读取；关闭或隐藏页面后不读取。菜单复用项目模型设置、目标暂停/停止和任务取消入口。UI 已在隔离数据下检查桌面与 390px 组件视口的明暗主题、输出查看与菜单焦点。没有完成全部宿主、全部旧版界面、Lighthouse 或真实模型验收。

Claude 新主脑／执行调用共用 `claude_output.py` 的消息块流参数与最终结果解析，使用 `stream-json`、`verbose` 和子代理文本转发，默认不启用逐 token 增量事件。原始消息块保存在原捕获文件中，可由现有只读检查器查看；没有把其内部工具调用自动画成新的消息线。只有当前主会话的唯一成功 `result` 才是完成证据，截断、错误结果、子会话终态、错误会话身份和终态后继续输出均被拒绝；退出码 0 不能替代该证据。总输出仍限 4 MiB，检查器每次仅取 32 KiB。当前未支持一个命令产生多个后台轮次终态，遇到此情形保留待核对。

流式格式依据本机 Claude CLI help 和[官方程序调用文档](https://code.claude.com/docs/en/headless#stream-responses)。真实本地子进程测试验证了退出前消息可见、主脑结构化动作提取和缺失终态时不写回；未调用真实 Claude 模型。Codex 参数另对照[官方配置示例](https://learn.chatgpt.com/docs/config-file/config-sample)与本机生成的协议 schema；effort 和服务层仍需按具体原生模型目录与账户核对，不能以任意字符串可解析作为实际支持证明。


## 生产事件推进的实际边界

host_events 与 goal_events 复用原项目数据库和 continuation driver。人类答复／阶段变化与事件原子保存，领取与原轮次同事务绑定；原扫描器仍为唯一派发入口。每批最多 64 项，主脑快照包含实际来源。已有轮次未知时继续原回执核对，不自动重发模型。

事件轮不改变周期及 next_due_at，到期轮合并待处理事件。退避和资源恢复设置持久 event_not_before；暂停、STOP、UNKNOWN、活动租约和 epoch 继续有效。自身审核事件归入当前轮。公共执行退出／审核入口已接项目范围同步，外部未归因会话不伪造实时事件。

这不代表参考 TaskGraph 已完成生产接线。生产任务图、持久记录的完整删除、原生主脑自编辑和工具保护、实际账户／宿主／安装验收及最终 PDF、Word 仍未完成。25 项事件用例使用真实临时数据库和 LangGraph、模拟原生模型，报告位于 .omo/qa/goal-events/report.json。

## 原执行队列的持久恢复

`host_queue_models/store.py`、`host_queue.py` 和 `task_queue*.py` 在原项目库中保存 queue_protocol=1 的任务回执。原阶段、原主脑轮次、epoch、请求摘要和完整启动输入摘要必须一致；任务与 prompt 各有 256 KiB 上限，回执 16 KiB。准备完成后才提交原线程池，没有新队列服务、模型轮询或续跑时钟。

入队、认领、实际 Python worker 启动前的 armed、PID 创建身份和等待结果分别记账。每次补投产生独立 delivery_id，旧回调被拒绝；入队回复异常先在原目标锁内撤销 token，避免已收到的回调逃逸。ACK 不回退已启动状态。DONE 只证明 launcher wait 返回，不代表模型成功或独立验收通过。

原扫描器每批最多检查 64 条可补投记录。只有已准备且未 armed 的任务，或其旧运行器已按 PID 和创建身份确认退出，才可补投原任务。存活和无法读取的运行器都不被当作退出；ARMED/STARTED 不重发。启动时保存可证明未启动的队列，以及精确确认仍存活的 launcher 和原阶段。取消会撤销未启动 token；STOP、准则、批准消费和当前开关仍在实际启动处校验。新旧回调、输入损坏及协议降级均有故障用例。

无效输入从自动补投集合移除，在原任务／阶段保留恢复原因；原始损坏内容不被替换为伪造记录。阶段认领到任务文件初始化仍不是跨 SQLite 与文件系统的原子操作：缺少队列准备回执时保留 UNKNOWN，不能凭一个 task.json 就把派发视为完成，也不能重建任务掩盖丢失的初始化。新托管任务的初始化清单与确定性补齐已在下节接入；没有该清单的历史任务仍不补造。数据库损坏后的修复、生产 TaskGraph 和真实掉电试验仍未完成。

队列专项 18 项、包含它的 41 文件工作台组 625 项通过，另有 114 subtests；日志和报告在 `.omo/qa/task-queue/`。这是临时原数据库与模拟执行器验证。没有真实 Claude/Codex 推理、部署或宿主 GUI 验收。

## 原任务初始化的确定性恢复

host_initialization_models/store/files 与 task_initialization、task_initialization_parent 把已解析的原任务输入、prompt、原模型／会话、预算初值、工程习惯及整改来源保存为私有清单。清单与阶段认领、批准消费在同一原项目事务中提交；随后才修改任务文件和父整改标记。清单最多 1 MiB，公开阶段日志只保留身份和摘要。

文件通过完成写入并 fsync 的临时文件发布到空目标，不覆盖已有目标；已有相同内容可重用，冲突或别名保留核对。原项目索引仍走原接口。初始化 READY 与原队列准备回执同事务提交，之后不再用初始快照覆盖运行结果。恢复沿用原动作核对入口，只补齐原任务；投递继续由原扫描器完成。没有新时钟或第二个任务，当前 STOP、准则与批准授权仍优先。

整改先保存 admission，再在原 review.lock 中验证原父任务和审核内容；只允许同一子任务自己的派发标记作为幂等差异。重复补齐不增加／重置整改次数，也不换模型或会话。认领后的授权拒绝保留未完成效果，不被当成“什么都没发生”的拒绝。已完成初始化后暂时无法入队，保留队列 READY 及当前授权等待原因。

新增初始化测试 9 项和两项真实公共整改链故障用例通过；联合工作台组 734 passed、1 skipped、114 subtests passed，跳过项需要配置好的 DSH 安装。首次 7 项扩展失败中，修复了只读上下文检查未统一规范化项目路径的实际问题；其余规范化测试临时路径，并将 HTTP 清理测试的进程表改为明确的空闲替身，生产保护未放宽。日志在 `.omo/qa/task-initialization/`。
