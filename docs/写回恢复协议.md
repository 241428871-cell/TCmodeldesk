# 原生 CLI 写回恢复

2026-10-23，隔离 worktree `native-langgraph`，未部署。Claude/Codex 共用此协议。用户已将崩溃验收限定为独立进程在持久化边界被强制终止、再由新进程恢复；不安排真实拔电或硬件缓存级验证。

## 行为

原生模型完成后，写回文件失败或进程中断，不应再次发送原提示。新编辑任务在模型启动前标记 `writeback_protocol=1`，原生结果与测试证据保存后才允许写回。带协议标记的任务没有完整回执时拒绝重新调用模型；不会把缺失回执当作从未执行。

成功结果保存于原任务目录：

- `native-cli/<capture_id>/proposed-files/`：只含声明文件的候选成果。
- `writeback-plan.json`：原始／候选内容散列、权限及缺失状态。
- `writeback-receipt.json`：任务／捕获身份、固定输入和 prompt 摘要、计划摘要、原生答复、测试证据、原队列投递身份。

清单与回执通过现有原子发布函数发布完整内容，不覆盖已有版本；POSIX 首次链接和已有完整记录的幂等重试都会 `fsync` 父目录。测试失败或超时也保留已产生的候选，回执明确不可应用。候选属于私有运行成果，不应提交到源码仓库。

## 恢复入口

复用现有 `POST /api/tasks/<task_id>/recover` 与 `confirm=true`。面板、Codex MCP、DSH loopback 使用相同后端。恢复按钮保留既有确认流程；没有新增计时器，也没有自动重发提示。回复提示采用实际后端结果，文件恢复完成不再显示“重新排队”。

服务端识别写回标记后走 `cli_writeback.recover`，不经过模型执行队列、不运行测试命令、不改账户和费用记录。恢复须满足：

1. 原任务处于 `recovery_pending`，没有取消标记，尚未通过独立验收。
2. 原 worker／launcher／child 均能确认已结束，当前工作台也未执行该任务；不可读进程状态不能当作退出。
3. 项目、阶段、文件范围、原代次及固定输入仍相同，当前目标授权仍允许执行。
4. 同一进程的项目／文件租约可立即取得，否则直接报告忙，不阻塞等待。按原任务的写回锁串行处理重复请求。
5. 捕获路径无链接越界，回执和清单完整且身份匹配，候选内容未变化；有测试命令时必须有成功证据。
6. 托管任务的队列 task／ticket／delivery 必须匹配原回执，状态必须为 armed、started、unknown 或 done。改变过的投递、未启动队列不能借此写回。

写回完成后仅将同一次原调用的队列核对为 done，任务记为 completed，进入原独立验收；不会自动接受成果。费用未知计数等已有计量保持原值。已精确写入的候选跳过，不重复修改文件；回执补齐会包含这些已写入文件。

## 中断与拒绝

| 情形 | 处理 |
| --- | --- |
| 替换后、task.json 更新前中断 | 比较文件实际版本，跳过精确已应用项，补齐剩余文件及回执 |
| 队列 done 后、任务 completed 前中断 | 幂等核对同一投递，补齐任务记录 |
| 人类修改、输入或候选变化 | 保留原文件及候选，不覆盖，不重发模型 |
| STOP／取消／验收已完成／原进程不明 | 拒绝恢复，保留原义务与证据 |
| 测试失败／超时 | 保存不可应用的候选，交由原整改与独立验收流程处理 |
| 回执尚未发布便中断 | 保留待核对；不能猜测模型未执行或拼接不完整证据 |
| 旧写回候选没有新协议回执 | 不伪造回执，也不降级为重跑模型 |

## 边界

当前是显式恢复入口，不是无条件自动恢复。进程退出采用原有进程身份核对，不把文件存在当作退出证明。没有新增跨进程资源租约：原任务写回锁只防重复恢复同一任务，不能代替不同任务之间的跨进程文件锁。

POSIX 单文件替换在临时文件 `fsync`、原子 rename 后同步父目录；新建的嵌套父目录也逐级同步其目录项。两文件生产恢复现由独立控制器执行：第一文件完成持久替换并记录进度后，测试进程收到 `SIGKILL`；全新恢复调用只补第二文件、不重复模型调用，随后结算原队列。该行为验证可重入的批次恢复，不代表多文件“全有或全无”事务。外部编辑器不遵守工作台锁时，末次检查与替换之间仍有竞争。模型运行尚未产生有效结果、测试进程无法创建等早期失败不保证保留候选。已有候选不包含未声明文件。各副本测试成功仍不能代替最终组合产物的独立验收。Windows 已由用户从范围排除。

任务 `task.json` 的原子替换同样先同步临时文件、再同步目标父目录；新建运行目录逐级同步，因此文件恢复需要的状态、capture id、租约 token 和费用未知调用计数具备相同的 POSIX 持久发布语义。首次租约库使用 initializing／ready 两阶段 identity marker，完整临时 SQLite 原子发布后才准入；独立控制器在两个边界直接退出后，下一进程已验证可恢复。ready／旧版 marker 对应的数据库缺失仍拒绝自动重建。交付验收不外推到存储设备缓存、挂载参数或真实供电故障；这些不再是本项目义务，也不能据此声称硬件级持久性。

DSH/Pi/WorkBuddy/Aider 的就地执行没有因此获得该临时副本协议。主脑移交、费用授权、原生权限与全局规则不变。
