# 跨主脑功能更新约定

## 隔离重构的侧栏、核对与消息流

本节仅描述 `feat/native-langgraph-control` 源码，未部署到已发布安装。Codex MCP 的 UI-only `panel_request` 现支持精确的项目模型、账户、治理、人工核对接口；原生输出 GET 只接受既有会话键、stdout/stderr 和 capture_id，不放行任意查询或 stdin。`panel_bundle` 按 index 的顺序内嵌全部已声明静态资产，避免宿主页面遗漏侧栏、治理、消息流脚本。读取资源、列工具、导入模块不启动服务或模型。

DSH 插件继续通过当前原生会话的可信项目打开同一 loopback 页面，使用公共 Handler、账户和治理核心，不需要复制 Codex MCP 代理。macOS desktop 安装器现已接 `.app` ASAR 静态身份核对、`launchctl` 用户环境适配和只读进程身份检查；DSH 执行端也使用同一 macOS 应用发现、ASAR 版本与官方 CLI 核对。本机已安装并核对 Node `22.23.4`、pnpm `10.26.0` 和 acpx `0.19.5`，执行端 `ready=true`；DSH `0.2.1-rc.2` 插件 0.2.12 已通过正式升级 prepare/check/install/check，收据、profile 和配置指针一致。安装期间 DSH 保持退出且没有调用模型。重开后又在原生 DSH 右侧栏验证了项目会话绑定、项目／模型树、Codex 与 Claude 原生目录以及官方登录钱包；真实 DSH 最小只读任务已验证 0.2.12 权限传播：mutations_allowed=false、host_access.mutations=read_only，brain_review 在插件守卫处拒绝；此前 0.2.11 将只读会话误判为可写的结果作废。

消息流的工具／子代理列也属于公共 `host_trace` 与 `flow_api`。已登记 Claude/Codex 原生 JSON 事件中的工具调用、命令和文件变更被投影为有界只读节点；确定的 `tool_result` 或 Codex `item.completed` 形成返回边。Codex 内嵌面板与 DSH loopback 页面读取同一投影，不复制解析器。节点不带工具正文、结果正文、stdin、PTY 或控制入口；其他没有结构化捕获的执行适配器继续明确显示未接入。隔离生产页面已实际显示命令、文件变更、发送与返回方向，这不等于两个宿主桌面外壳分别完成原生验收。

## 执行端访问权限

批准消费现由共用 `stage_store.claim_dispatch` 与 `decision_grants` 接入，Codex／DSH 的公共派发路径共用同一原事务和任务身份。原生执行器启动检查已有回执，不能自行生成批准。离线阶段／恢复回归覆盖这一边界；没有据此声称两个宿主原生 GUI 或全部内部工具调用已验收。

隔离重构中的人类例外通过公共 `human_decisions`／`decision_scope` 处理。Codex MCP 内嵌面板与 DSH loopback 面板走同一人类答复接口，新卡按受影响阶段与完整上游证据核对，旧卡和最终审核保持整目标范围。后台离线回归已覆盖原项目库、并发答复及受控写回锁；本轮没有重新做两个原生 GUI 验收，批准消费与真实事件推进已接共用核心；Claude 新主脑入口及生产任务图细粒度恢复仍未据此完成。

Codex/DSH 共用 Pi、DSH、WorkBuddy 卡片内“参数设置 → 模型与连接 → 访问权限”。选择后立即保存，按执行端应用于其全部模型；Pi/DSH 未保存时保留既有完全访问。新任务由控制器记录权限快照，正文参数不能覆盖；排队、运行、恢复、续接与整改保持原任务权限，历史 Pi/DSH 无快照任务按原完全访问处理。只读聊天不获得写入或终端权限。

DSH 项目范围使用原生 `workspace-write` 策略并追加工具参数校验，完全访问使用 `danger-full-access`；Pi 项目范围只有工具参数校验，没有操作系统沙箱。两者的显式路径检查处理真实路径/目录联接及常见终端字面路径，无法推断任意脚本动态计算的路径；工作台记录保护始终生效。文件统计仍只覆盖声明文件，不是全盘审计。更新保护代码后旧原生会话可能因指纹变化拒绝续接，应创建新任务，不隐式换会话。

本次验证包括保存与任务快照的离线控制器测试、Codex/DSH 浏览器模拟视图、已安装 Pi/DSH 执行器连接本地模拟提供方的工具测试；不代表消耗真实模型额度的任务验收或两宿主桌面 GUI 人工验收。

通用能力更新必须覆盖全部已支持的主脑；当前为 Codex、DSH。WorkBuddy 尚在适配中，不算已完成支持。这里的全局是当前安装及其本机项目，不意味着其他电脑或尚未适配的 Agent 自动获得能力。

## 更新步骤

1. 先判断通用核心还是宿主专属功能。范围、路由、验收、记录、状态语义等优先复用公共实现；原生入口、账户来源、消息唤醒由适配器接入。
2. 列出 Codex、DSH 的触发入口、共享实现和生效方式。新宿主沿用同一行为契约，缺少原生能力要明确显示未支持，不伪造等价能力。
3. 为公共行为及每个入口运行必要检查，覆盖项目未知、开关关闭、无可用候选、异常和正常路径。只读预检不得调用模型、派发任务、创建项目记录或为了提示启动服务。
4. 更新全局规则模板和安装器覆盖的入口；保留用户规则、设置、历史及已在运行的任务。已有聊天的旧指令和常驻进程不承诺热更新。
5. 分别记录源码检查、部署检查、真实宿主验证。仍有适配器缺失或未验证时如实列出，不能以一个宿主通过概括全局通过。

## 运行中进展查询与需求插入

公共 `goal_interactions` 现在区分只读 `/btw` 查询与版本化需求插入。需求保存在项目领域库，按目标单调编号；主脑轮次记录自己读取的需求版本，只能在成功结算时核销该版本及以前的 pending 需求。在途轮次期间新到的需求保持 pending，并将下一轮设为到期，不撤销人工暂停或 STOP，也不会被旧轮次冒充为已经处理。普通增量需求由执行链在副作用边界读取新版；显式方向调整还会在需求提交后持久请求旧主脑和受影响任务停止。生产动作链在每个副作用边界核对 claim 的需求版本；版本变化时旧动作批以 `superseded` 持久结算、停止后续写入和派发，下一轮从公共领域事实重建。派发任务同时保存原轮次需求版本：尚未启动的旧队列原子退休，运行中的 CLI 子进程沿公共取消边界停止，已保存但未写回的候选保留且原项目不修改，缺版本的受管记录按未知阻断。被需求淘汰的精确最后任务同时在阶段领域记录留痕；替代执行等待原进程退出证明与租约释放，下一轮不能改写旧阶段，而是把它作为可查询的 superseded 历史并创建后继阶段。中断回执明确区分已请求、无需中断和待修复，相同请求可重放修复 incomplete 回执。该语义属于调度核心，Claude、Codex 与 DSH 适配器不能各自实现不同的处理方式。

工作台通过项目限定、面板令牌保护的同一接口提供 `/btw 进展` 和“插入最新需求”。消息流中的决策／执行节点也按自身真实 `goal_id` 打开同一治理对话框，因此从 CLI 会话追踪到目标控制不依赖当前目标下拉选择、不复制写入逻辑。host-neutral `brain_mcp_server` 与 Codex 全局 MCP 又把同一核心暴露成模型可见 `goal_interact`：受信 brain 入口的项目不可由调用参数覆盖，Codex 入口从线程元数据、唯一 root 或显式绝对路径解析项目；项目有且只有一个活动 Goal 时可省略 goal_id。2026-10-23 已在隔离项目上由真实 Codex `gpt-6-luna` 和 Claude canonical `claude-haiku-5-5` 分别完成查询与版本化写入；同日随机端口真实面板又完成“流节点 → 查询 → 插入 → 再查询”的临时项目闭环。这里验证的是模型按工作流规则调用 MCP 与工作台公共入口；宿主二进制没有硬编码 slash-command 拦截，旧聊天也可能需要新会话加载工具与规则。DSH 继续复用同一 brain MCP，但本轮未再启动真实 DSH。

同日另分别以真实 `gpt-6-luna` 和 `claude-haiku-5-5` 验证需求被下一主脑轮实际处理，而非只停在 MCP 写入：两个一次性项目的 R1 方向调整均经公共生产 GoalGraph 生成两阶段动态计划，持久依赖、计划修订和 applied 回执成立，且两轮都没有派发执行任务。Codex 验收完整退出0。Claude 轮的计划、依赖、需求、零任务、会话和原生 auto 权限回执依次通过；验收脚本最后把实际 `macos-seatbelt-workspace-write` 围栏标签误写成旧简称而退出1，失败发生在上述产品断言之后，未据此把测试脚本整体伪称全绿，也未重复调用模型。

项目树的决策模型活动状态同样来自 host-neutral 的持久 Goal 回执，不从 Codex、Claude 或 DSH 窗口是否打开来猜测。claimed／started／unknown 分别显示启动中／已启动／待核对；执行模型仍从任务记录统计。读取前确认项目记录库存在，空项目侧栏不会初始化记录或启动宿主。各宿主打开的是同一公共工作台，因此无需复制状态适配器。

项目树的模型右键也只把项目、模型 ID 与角色交给公共消息流定位器。找到的节点继续走同一 `flow_api` 输出读取和治理／任务控制；找不到就说明当前窗口无真实会话，不启动 CLI 或创建宿主占位记录。Codex MCP 内嵌面板与 DSH loopback 页面因此共享相同行为。

跨项目工程习惯也由公共 `engineering_policy` 生成不可变快照，Claude/Codex 主脑和所有执行入口保存同一快照，不由宿主各自拼接。全局文件只保存可复用模板；项目覆盖存于项目自己的 `.model-desk` 并使用独立版本，一个项目编辑不会推进其他项目的覆盖版本。旧全局项目映射只读兼容，下一次显式保存时迁移。治理界面从 GoalGraph 的持久 snapshot/native 阶段读取某个目标最近实际加载的快照与确认状态；当前设置与在途快照不同就显示“待下一轮”，读取失败保持待核对。该查询不启动模型、不创建项目记录，也不读取原生输出正文。

主脑所有者移交同样只走公共 `goal_controller/control_goal('handoff')` 与 `host_handoff`，宿主适配器不能自行替换会话或跳过 owner_epoch。2026-10-23 已在一次性项目用真实 Codex、Claude、Codex 三轮生产主脑完成双向移交：每次都先结算、显式暂停、清空旧会话并递增 owner_epoch，恢复后才启动新所有者；第二次 Codex 启动没有复用第一次会话。该证据覆盖 Claude/Codex 原生 goal runner，不扩大为 DSH/Pi 主脑支持。

## 执行端独立开关

执行端卡片、自动路由模型选择和启用状态由公共 `execution_endpoints` 维护；Codex/DSH 共用相同路由、候选、启动前与恢复检查。禁用不取消已运行任务，不更换既有 Agent 或模型，不修改范围和预算。WorkBuddy 原生执行队列已接入这两个主脑的公共控制器；新任务的原生开发工具、固定原生模型、未知费用和安全恢复限制同步适用，旧任务保持原限定文件配置。两宿主模拟检查与真实任务验收分开记录：Codex CLI 的单文件真实闭环已通过，DSH 原生入口派发 WorkBuddy 仍待实测。WorkBuddy 作为主脑仍未适配完成。详见 [EXECUTION_ENDPOINTS.md](EXECUTION_ENDPOINTS.md)。

DSH 作为执行端时有一项宿主适配器限制：macOS 任务只通过已核对应用包安装的官方 `dsh` CLI 后台运行，不启动或唤起桌面主进程。公共执行端状态传递 `ui_policy=background-only` 供 Codex 内嵌面板和 DSH loopback 面板显示；CLI 缺失时适配器 fail closed，宿主页面不得自行回退到 GUI 启动。CLI 更新检查属于共享执行端能力；实际更新必须识别安装来源，签名应用内的 DSH/Codex 交给宿主应用更新，Claude 原生安装才调用 `claude update`。

WorkBuddy 内置模型选择也属于共享执行端能力：Codex/DSH 共用卡片、原生目录缓存、独立模型标识、选择持久化和旧任务模型保持规则。模型列表读取不生成内容，不更改其他执行端或预算。两宿主模拟页面覆盖读取/保存信封与刷新保留选择；Codex CLI 已分别对 DeepSeek V4.1 Flash、GLM-5.3-Flash 完成真实单文件独立验收，其他模型仍需单独实测，DSH 原生派发 WorkBuddy 仍未据此验收。

任务模型与 Agent 的兼容性也位于公共工作台，不由 Codex 或 DSH 页面分别实现。Claude／Codex／WorkBuddy 原生模型只允许同名原生执行端；本地和 API 模型禁用这些原生端并恢复 DSH／Pi 等通用执行端。切换模型时完整重算选项，避免前一个模型的禁用状态残留。会话文案同样共享：当前只有 DSH／Pi 能继续任务 Agent 会话，Claude／Codex／WorkBuddy 每个任务新建会话。隔离生产前端已实际往返点验；这不等于 DSH 原生 GUI 已单独验收。

## 原生 PowerShell 7 依赖

Codex MCP、DSH/通用主脑的公共启动器、系统目录选择器共用 `powershell_runtime.find_pwsh`。调用宿主的 PATH 不应决定相同机器上是否能启动。现有 PowerShell 7 可来自系统安装、显式绝对路径或本机缓存；不要求 Codex 运行，但仍依赖该可执行文件实际存在。没有原生 PowerShell 时明确拒绝，不自动下载、不换 shell。

独立启动验收必须区分“已有后台时复用”和“无后台时冷启动”。只检查复用不能证明独立启动。`probe_panel_cold_start.py` 在临时安装中运行真实启动脚本，以不含 Codex 环境/PATH 的环境启动 fixture HTTP 服务并复用，模型/记录/真实端口均不参与；实际桌面验收另记。

## 执行端设置弹窗与统一预设

Codex/DSH 共享紧凑卡片、设置弹窗首页及四项执行端预设；模型连接在第二页签。`execution_endpoints.apply_preset` 按最终执行 Agent 合成有效能力，路由与主脑候选共同使用；旧任务保留快照。未保存时沿用各模型原预设，不自动迁移。实际模型价格、账户与预算不合并。WorkBuddy 作为执行端使用同一预设，作为主脑仍未适配。本次为离线控制器及两宿主浏览器视图检查，不等同原生推理验收。


## WorkBuddy 原生开发工具

Codex 和 DSH 共用 `panel_server` 派发时的工具配置/代码指纹快照、`workbuddy_worker` 和受信原生宿主通道；候选返回相同的原生开发/终端能力。普通任务及正式主脑任务统一适用只读/编辑权限、记录保护、自测证据与独立验收。新工具配置不升级旧排队任务及其整改。两宿主 mock 控制器和页面检查与原生实测分开记录；不能把 Codex 真实任务通过概括成 DSH 原生 GUI 已实测。详见 WORKBUDDY_EXECUTOR.md 的原生开发工具章节；第三方扩展、子代理与发布工具不包含在本次 12 项配置中。

WorkBuddy 原生工具初始化与公共派发入口统一接受项目内的绝对/相对文件路径，仍解析实际路径拒绝项目外目标和别名。该修正位于共享执行器，Codex/DSH 都适用；两宿主在全新临时项目中的编辑与只读绝对路径请求有隔离回归，真实用户项目复验另记，不自动重派旧任务。
